# 03 — Data model (Postgres) and migration

Managed by Alembic; this DDL is the shape of the baseline migration, not a hand-run script.

## Target schema

```sql
CREATE TYPE ticket_priority AS ENUM ('low', 'med', 'high');
CREATE TYPE ticket_status   AS ENUM ('open', 'closed');

CREATE TABLE users (
    id     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- BY DEFAULT: migration inserts legacy ids
    email  TEXT NOT NULL UNIQUE,
    name   TEXT NOT NULL
);

CREATE TABLE tickets (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title       TEXT NOT NULL CHECK (btrim(title) <> ''),
    slug        TEXT NOT NULL,
    priority    ticket_priority NOT NULL DEFAULT 'med',
    status      ticket_status   NOT NULL DEFAULT 'open',
    assignee_id BIGINT REFERENCES users(id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    closed_at   TIMESTAMPTZ,
    CHECK ((status = 'closed') = (closed_at IS NOT NULL))
);
CREATE INDEX tickets_status_created_idx ON tickets (status, created_at DESC);
CREATE INDEX tickets_created_idx        ON tickets (created_at DESC);
-- Slug uniqueness: DO NOT add a UNIQUE constraint until Q1 is decided.
-- Legacy data contains colliding slugs; a unique index would fail the migration.
CREATE INDEX tickets_slug_idx ON tickets (slug);

CREATE TABLE reset_tokens (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       TEXT NOT NULL,
    token_hash  BYTEA NOT NULL UNIQUE,        -- sha256 of the token; plaintext never stored
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ NOT NULL,          -- created_at + 30 min (config)
    used_at     TIMESTAMPTZ                    -- single-use marker
);
CREATE INDEX reset_tokens_email_created_idx ON reset_tokens (email, created_at);

CREATE TABLE outbox_emails (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    recipient    TEXT NOT NULL,
    body         TEXT NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    sent_at      TIMESTAMPTZ,
    attempts     INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_error   TEXT
);
CREATE INDEX outbox_pending_idx ON outbox_emails (next_attempt_at) WHERE sent_at IS NULL;
```

Notes:
- `closed_at`/`status` CHECK encodes the invariant legacy maintained informally. Verify
  legacy data satisfies it during migration; if legacy rows violate it (e.g. closed with
  NULL closed_at), set `closed_at = created_at` and log the repair.
- Priorities/status as enums: legacy CHECK constraints guaranteed only these values exist,
  so migration is safe. NULL priority is possible in legacy (CHECK permits NULL): migrate
  NULL → `'med'` and log counts (matches the API default).
- Slug column keeps legacy values verbatim during migration regardless of Q1's outcome.

## SQLite → Postgres migration

One-shot script `scripts/migrate_from_sqlite.py` (Phase 5 of the plan):

1. Open `ticketd/db/ticketd.sqlite3` read-only. (The file is not in the repo — it lives on
   the prod host. The script takes its path as an argument; see Q8.)
2. Copy `users` (preserve ids), then `tickets` (preserve ids), in id order.
3. `created_at`/`closed_at` are naive **local-time** strings. Convert using the legacy
   host's timezone (script argument `--source-tz`, see Q5/Q8) → UTC timestamptz.
4. **Do not migrate `reset_tokens`.** Tokens live 30 minutes; any rows are expired garbage
   (and MD5). Start empty.
5. Reset both identity sequences: `setval(pg_get_serial_sequence('tickets','id'),
   max(id))`, same for users.
6. Emit a verification report: row counts per table, min/max ids, per-status and
   per-priority counts, count of NULL-priority repairs, checksum of
   `(id, title, status)` tuples — compared against the same query run on SQLite. The
   cutover checklist (verification V-11) requires this report.

Idempotency: the script must either refuse to run on a non-empty target or support
`--wipe-target`. Cutover requires a write freeze on legacy (see plan, Phase 6).
