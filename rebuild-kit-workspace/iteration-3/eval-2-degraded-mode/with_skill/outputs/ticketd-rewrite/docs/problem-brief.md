## Motivation

`ticketd` is an internal ticket tracker inherited from a contractor with no git history, no
access logs, and (for the next few weeks at least) no production database access. The rewrite is
commissioned now, ahead of that evidence arriving, on the explicit instruction to generate the
workspace immediately and layer evidence in later via spec-patch mode. Target stack for the
rewrite is FastAPI + Postgres (human decision, recorded in `rebuild.json`). Two defects are known
from the handover notes; everything else about production behavior, traffic, and data shape is

## Register

### PB-001 — Notification emails send synchronously inside the request, blocking it
- kind: defect
- severity: high
- reported_by: contractor handover notes (relayed by task owner)
- affected_area: `app/server.py` (`close_ticket`, `request_reset`), `app/notify.py`
- detail: Both `close_ticket` (legacy/app/server.py:67-77) and `request_reset`
  (legacy/app/server.py:80-95) call `send_mail()` inline before returning a response.
  `send_mail` (legacy/app/notify.py:1-7) opens a blocking SMTP connection with a 30s timeout
  in-request. The module docstring states "Blocks the request thread; ~2s typical, 30s on
  provider trouble" (legacy/app/notify.py:1), and the call site is commented "sends
  synchronously in-request; SMTP outages take ticket-closing down with them"
  (legacy/app/server.py:75). This means an SMTP outage or slowdown makes ticket-closing and
  password-reset requests themselves slow or fail, even though neither operation logically
  depends on mail delivery succeeding.
- reproduction: Not reproduced against a live instance (no environment available this run).
  Code-evidenced via the citations above; corroborated by the module's own docstring.
- disposition: REPAIR in WO-004 (dispatch email asynchronously via an outbox/queue so
  ticket-closing and reset-token issuance no longer block on SMTP; see
  `docs/open-questions.md#OQ-002` for the one open sub-question on delivery guarantees)

### PB-002 — Password-reset tokens are generated with MD5
- kind: defect
- severity: high
- reported_by: contractor handover notes (relayed by task owner)
- affected_area: `app/server.py` (`request_reset`), `db/schema.sql` (`reset_tokens`)
- detail: `request_reset` derives the reset token as
  `hashlib.md5(f"{email}{time.time()}".encode()).hexdigest()` (legacy/app/server.py:90), commented
  in the source as `# md5, single table`. MD5 is not a credential-grade primitive (fast to brute
  force, not designed for unpredictability under a known/guessable input like `email + timestamp`),
  which weakens the reset flow's core security property: an attacker who can narrow the request
  timestamp has a tractable search space for a live token.
- reproduction: Not reproduced against a live instance (no environment available this run).
  Code-evidenced via the citation above.
- disposition: REPAIR in WO-003 (issue tokens via a CSPRNG — e.g. `secrets.token_urlsafe` — sized
  for negligible collision/guess probability; preserve the observable outcome behaviors: 30-minute
  expiry, rate limiting, non-disclosure on invalid/expired, single-use)

## NFR targets

- NFR-001 — Ticket-closing and password-reset-request endpoints must not block on outbound email
  delivery (derived from PB-001). Target: p99 request latency for these two endpoints independent
  of SMTP provider latency/outage.
- NFR-002 — Reset tokens must be generated by a cryptographically secure random source, not a
  hash of guessable/low-entropy inputs (derived from PB-002).
