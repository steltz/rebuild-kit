# Zero-Traffic Report

Observed window: 1 days · 2000 matched requests

**Evidence-quality caveat (see `rebuild.json.evidence.notes` and `docs/open-questions.md#OQ-003`):**
the rewrite request described "a ~30-day access log," but the supplied file
(`ticketd/ops/access.log`) is a single calendar date (`12/Jul/2026`) with timestamps that cycle
through the same ~61-entry HH:MM:SS pattern repeatedly, one synthetic user
(`jdoe@corp.example.com`), one user-agent (`svc-ui/2.1`), and randomized source IPs. Endpoint
*frequency ratios* are reasonable evidence (independently re-verified during P9 audit, exact
match); *temporal coverage* (a real 30-day window, weekday/weekend cycles, multiple real users) is
not present. Treat "zero traffic" below as a same-day observation, not a 30-day one.

**Update (P9 audit, 2026-08-09):** status-code mix is **not** fully trustworthy at the
per-endpoint level — of 423 `POST /api/tickets` requests, 411 show `200` and zero show `201`, but
the pinned commit's `create_ticket()` unconditionally returns `201` on success
(`ticketd/app/server.py:55`, confirmed by every P7 trace). This log was not literally generated by
running this exact commit; it's synthetic traffic-shape data. Error-rate percentages (5xx/429
counts) were independently re-checked and do match exactly, so PB-004's 2.55% figure stands, but
"status-code mix is reasonable evidence" (as originally claimed above) is now known to be false at
least for this one case — corrected rather than left standing.

Routes in code with no observed traffic. Zero-traffic ≠ dead: check window coverage (cron/seasonal), admin paths, webhook receivers. Promote to do-not-port.md only with corroborating static evidence.
