## Discrepancies (each has been applied to the specs — this is the record)

### AD-001 — `ticket.json`'s slug `pattern` is false for real legacy output (WO-002, `docs/contracts/schemas/ticket.json`)
- verdict: contradicted
- counterexample: a title that is non-empty-after-`.strip()` but all punctuation (e.g. `"!!!"`)
  slugifies to `""` via `ticketd/app/util.py:4-6` — `create_ticket()`'s only validation is
  whitespace-strip, which doesn't catch this. Separately, `.strip("-")` runs *before* `[:64]`
  truncation in `util.py:6`, so a title whose 64th slugified character lands on a hyphen produces
  a slug ending in `-`. Both independently re-verified by the generator via direct execution of
  `slugify()`. The schema's `pattern: "^[a-z0-9]+(-[a-z0-9]+)*$"` is false for both cases.
- action taken: removed the false `pattern` constraint from `ticket.json`, replaced with a
  citation-backed description of both edge cases so an implementer doesn't validate against a
  guarantee legacy doesn't keep.

### AD-002 — access log's per-endpoint success status codes don't match the pinned commit (evidence quality, `ticketd/ops/access.log`)
- verdict: contradicted
- counterexample: 411/423 `POST /api/tickets` requests in the log show status `200`; zero show
  `201`. `create_ticket()` unconditionally returns `201` on success (`server.py:55`, confirmed by
  every P7 trace). Independently re-verified by the generator via `awk` against the raw log.
- action taken: added an explicit note to `rebuild.json.evidence.notes` and `zero-traffic.md`
  stating the log was not literally generated by running this exact pinned commit — it's
  synthetic traffic-*shape* data. Frequency ratios and error-rate percentages were separately
  re-verified and do hold up arithmetically, so PB-004's usage-weight/error-rate figures stand,
  but status-code-specific claims from the log are no longer represented as trustworthy.

### AD-003 — `?status=` (empty value) does not "return an empty array" the way WO-000's original phrasing claimed (WO-000, WO-002)
- verdict: contradicted
- counterexample: `request.args.get("status")` returns `""` for an empty query value;
  `if status:` (`server.py:32`) treats `""` as falsy, so no filter is applied and the *full*
  unfiltered list returns — not an empty array, contrary to WO-000's original "any other value...
  returns an empty array" phrasing.
- action taken: corrected WO-000's statement to scope the "empty array" claim to non-empty junk
  values only, and added the empty-string case explicitly to both WO-000 and WO-002 with a
  cross-reference. Not yet captured as a trace (see OQ-011).

### AD-004 — trace note cites a `diff-rules.yaml` normalization rule that doesn't exist (`verification/replay/traces/auth-reset.jsonl`, trace `reset-confirm-success-002`)
- verdict: contradicted
- counterexample: the trace's note claimed "token value normalized in request for reproducibility
  -- see diff-rules.yaml"; `grep` against `diff-rules.yaml` finds no token-related `normalize`
  rule anywhere in that file (confirmed by both the auditor and the generator).
- action taken: rewrote the note to correctly describe the `<CAPTURED_TOKEN>` placeholder as a
  fixture-authoring convention, not something `diff-rules.yaml` governs.

## Findings demoted to unverifiable (not contradicted, but the evidence backing them was weaker than claimed)

### AD-005 — PB-004's "three consecutive database-is-locked 500s" reproduction claim (`docs/problem-brief.md`)
- verdict: unverifiable (downgraded from an earlier "directly reproduced" framing)
- gap: the specific "three consecutive 500s" detail was only observed transiently during the
  generation session's terminal output and never saved to a committed artifact (no raw log, no
  traceback file in the repo). The only committed artifact, trace
  `tickets-crud-lock-cascade-901`, shows a *successful* follow-up request, not a locked one — its
  own note already said so, but PB-004's prose overstated the reproduction as settled fact.
- action taken: PB-004 rewritten to distinguish the **mechanism** (leaked SQLite connection, no
  `teardown_appcontext` — independently, statically verifiable by reading `server.py:20-24`,
  still solid) from the **specific incident detail** (now framed as "observed once transiently,
  not preserved as evidence" — a strong hypothesis, not a proven fact). Reproduction steps for
  capturing it properly are documented for whoever picks this up next.

### AD-006 — "expired" trace citation conflates a consumed token with a genuinely time-expired one (`docs/domain/reset_token.md`, WO-003, WO-004, `verification/replay/traces/auth-reset.jsonl`)
- verdict: unverifiable (the underlying FIXED claim is still confirmed by direct source reading;
  only the *trace evidence* backing it was overstated)
- gap: `server.py:103`'s non-disclosure check has two disjuncts — `row is None` (not found /
  already consumed) and a time-based expiry check. Trace `reset-confirm-already-consumed-003` was
  cited (including in its own now-corrected note) as covering the "expired" case, but it actually
  hits the *first* disjunct (its token was deleted by a prior successful confirm), not the second.
  **No trace in the corpus exercises the genuinely-expired-but-still-present-row branch.**
- action taken: corrected the trace notes and WO-003's evidence citation to say precisely what's
  covered and what isn't; added to OQ-011's scope (blocks WO-003's close until a real
  time-expiry trace is captured — see that WO for the repro recipe: mint a token, wait past the
  30-minute window or manipulate `created_ts` in a test DB, then confirm).

## Coverage-hunt findings (new spec items — action: added to WO-002/PB-011, see `docs/open-questions.md#OQ-011`)

1. Non-object JSON body to `POST /api/tickets` (e.g. `[]`, `"hello"`, `42`) → `AttributeError` →
   unhandled 500. Same family as OQ-008, distinct trigger. (`server.py:42-43`)
2. Explicit `{"priority": null}` → `str(None)` = `"None"` → DB CHECK violation → unhandled 500.
   Distinct from the already-traced invalid-string-priority case. (`server.py:47`)
3. Non-numeric id on `POST /api/tickets/<id>/close` was never verified end-to-end (only the `GET`
   equivalent was traced) — presumed identical by analogy, not confirmed.
4. (Auth/Reset module, informational only, not actioned as a required gap) — the token-hash input
   and the `created_ts` column value come from two independent `time.time()` calls
   (`server.py:90` vs. `:92`), not one shared clock read. No behavioral consequence found; noted
   in `docs/domain/reset_token.md` for whoever designs WO-003's replacement.

None of these four are believed to change any FIXED/REPAIR/FREE disposition already assigned —
they're gaps in evidence and documentation completeness, not newly-discovered behavioral
surprises that contradict what was already claimed elsewhere.

## What this audit did not do

- Did not attempt symbolic execution or exhaustive branch enumeration — findings came from careful
  manual reading of a small (165 LOC) codebase by two independent agents plus generator
  spot-checks, not from a tool that can guarantee completeness. `branch_coverage_pct` in
  `metrics.json` is explicitly labeled an estimate for this reason.
- Did not re-audit P0-P8's non-behavioral artifacts (CLAUDE.md files, ledger/rebuild.json schema
  conformance, harness script correctness) — those were validated at the time each phase produced
  them (see each phase's commit) and P9's mandate is specifically the behavioral spec/contract
  claims and problem coverage.
- Did not have production data or a genuine 30-day access log to audit against — every finding
  here is grounded in the legacy source code and the same evidence available to the original
  generation pass; this audit could not manufacture evidence that was never supplied.
